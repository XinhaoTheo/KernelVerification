# allclose 对抗案例种子集(12 个,后续滚到 100:50 FN + 50 FP)

- **FN(if the threshold is high this will all be decided as no-pass)**:kernel Has the bug,but if the verification allows the threshold,random or normal test will not detect this bug, toech.allclose will decide this as pass(correct)。

## FN Group

### FN1. NSA sparse attention select block (if 2 block have same value) bug
kernel: NSA(Native Sparse Attention)那种结构——先给每个 block 打分选出 top-k 个 block,再对选中的 block 做正常的 attention,最后输出连续的 attention 结果。fla-org 和 XunhaoLai 都有公开的 Triton 实现,是真在训练/推理里用的东西。

bug 是什么:更新"当前 top-k 里最小值"这个阈值的时候用了严格大于,没用大于等于。分数一旦打平(现实场景里很常见,比如两个 block 内容高度重复,或者精度不够被舍成一样的分数),后到的那个 block 会被错误地挤掉。

为什么 allclose 测不出来:如果测试用随机高斯分布生成 Q/K,fp32 精度下两个 block 分数刚好完全相等的概率几乎是零,随机测试根本触发不了这个并列分支,两种实现选出来的 block 几乎总是一样的,最后输出自然对得上。就算你专门构造了触发并列的输入,漏选的那个 block 也只是被 softmax 里其他很多项稀释掉了一点,最终输出的偏差可能还在常规容差(比如 rtol=1e-2)以内。

真正该怎么判断:去读选 block 那段代码,看阈值比较用的是 `>` 还是 `>=`,再专门构造几个"两个 block 分数强制相等"的输入去验证,而不是指望随机测试蒙对。

### FN2. 投机解码 accept 判断用确定性比较代替真随机采样
kernel 是什么:vLLM 有专门的 Triton rejection sampler kernel,用于投机解码里判断草稿 token 要不要接受。

bug 是什么:标准算法要求生成一个随机数 r,如果 r 小于 target 概率除以 draft 概率(且不超过 1)就接受;但 kernel 图省事直接比较两个概率大小,没有随机采样这一步。

为什么 allclose 测不出来:如果测试场景里 draft 模型和 target 模型本身就很接近(这也是投机解码最常见的评测配置),两种判断方式在大多数 token 上给出的接受结果差不多,短测试跑几十个 token 统计出来的接受率、输出分布看起来很接近,数值上过得去。但这个 bug 会让最终采样出来的 token 分布系统性地偏离 target 模型的真实分布——这是个统计意义上的偏差,不是某一次运行数值对不上,得跑大量样本做分布检验,或者直接读代码确认有没有真随机这一步。

真正该怎么判断:读代码确认 accept 逻辑有没有真的做随机采样,而不是看某次运行的数值误差。

### FN3. "规整配置掩盖不整除边界" 这个套路,在两个不同 kernel 上各来一次
这条本来是两个独立 case(GPTQ 分组量化边界、GQA 头映射),拆开看发现是同一个诡计——"测试用的配置永远是规整数字,边界/异常配置的代码路径长期没人跑过、没人验证过"——套在了两个不同 kernel 上。合并成一条,GQA 当成 GPTQ 那个的"延伸变体",后面扩展到 100 个的时候,这套路还能继续套在别的 kernel 上(比如矩阵乘法的 tile 大小、attention 的 seq_len 是不是 block_size 的整数倍)。

**主例子——GPTQ int4 分组量化的 group 索引错位**
kernel 是什么:AutoGPTQ 那套 Triton 融合 dequant+matmul kernel,int4 权重按 group(比如每 128 列一组)各自用一个 scale。如果开了 act-order 这个选项,列的顺序会按"重要程度"被打乱,这时候每一列该用哪个 group 的 scale,不再是简单的除法能算出来的,得靠一张单独的映射表(g_idx)去查。

bug 是什么:g_idx 这张表本身构造错了,或者 kernel 读取索引的时候错位,导致某几列被安排去用了别的 group 的 scale 做反量化。

为什么 allclose 测不出来:大部分 benchmark 测试用的矩阵形状都是"整齐"的(比如 hidden_size 能被 group_size 整除),而且大多数测试根本没开 act-order 这个选项去专门验证 g_idx 对不对,这条代码路径长期没被真正跑到过、也没人认真检查过映射关系。

**延伸例子——GQA 的 query 头到 KV 头映射公式写反**
kernel 是什么:分组查询注意力(GQA)的 attention kernel,query 头要按组映射到共享的 KV 头。

bug 是什么:映射公式本该是"用组数整除",kernel 写成了"对 KV 头数取余数"。

为什么 allclose 测不出来:标准测试用的头数配置几乎都是 2 的幂这种规整组合(比如 32 个 query 头、8 个 KV 头),没人拿"不整除"或者非标准的头数比例去测,这块映射逻辑同样是测试盲区,跟 GPTQ 那个案例是一模一样的套路。

真正该怎么判断:两个案例都一样——专门检查边界/映射公式对不对,再拿"不规整"的配置(不能整除的形状、开了 act-order、非标准头数比例)去测,而不是只用默认的规整配置跑一遍就算过了。

### FN4. INT8 量化的 scale 算法跟不上真实数据的离群值(新补的机制)
kernel 是什么:INT8 量化的 matmul,权重和激活值都压成 int8 做推理加速,这是很常见的推理优化手段。

bug 是什么:scale 本该用当前这批数据实际的最大值去算,kernel 却用了历史数据的滑动平均最大值(EMA)。

为什么 allclose 测不出来:这条不是"测试场景没覆盖到"那一类,是"测试用的数据分布本身跟真实数据不一样"。如果测试用的是普通随机初始化的张量(比如标准正态分布,数值都比较"温和"),数据里没有明显的离群值,EMA 算出来的 scale 跟实时算出来的 scale 差不多,测试很容易过。但真实训练出来的大模型,权重和激活值里经常有个别通道的数值特别大——这是 LLM.int8()、SmoothQuant 这些论文专门讨论过的真实现象,业内叫 outlier feature。换成真实模型的数值分布去跑,EMA 跟不上这些离群值的变化,同一批数据里那几个真正的大数会被严重 clip,精度损失很明显。

真正该怎么判断:不能只用随机初始化的张量测,得用真实训练出来的模型权重/激活值分布(或者至少专门构造带离群值的测试数据)去测,同时读代码确认 scale 是不是用当前 batch 的真实值算的,而不是某种历史平均。

### FN5. KV cache 量化的误差随生成长度累积
kernel 是什么:类似 TurboQuant 这种把 KV cache 压缩到 3bit 的方案,Google Research 2026 年发的,号称精度几乎不掉。

bug 是什么:量化用的旋转矩阵/codebook 计算有个小错误,单步看误差很小。

为什么 allclose 测不出来:这里要澄清一下,不是 allclose 这种比较方式本身有什么先天缺陷看不见它——如果真拿长序列生成的结果去比,偏差迟早会大到能被任何合理的容差卡出来。真正的问题是标准的 kernel 单元测试,默认模式就是"跑一次前向,比一下输出",压根没有测过长序列生成这个场景。所以这条本质上也是"测试场景覆盖不够广"这一类(跟 FN3 那条是同一个大类,只是一个是没测过不整齐的配置,这个是没测过长时间累积的场景),不是数值比较方法本身的锅。

真正该怎么判断:不能只测单步前向,要专门测长序列生成后的整体质量退化,或者直接读量化算法(旋转矩阵/codebook 的推导)是否正确。

### FN6. RMSNorm 的 eps 加法位置错误
kernel 是什么:RMSNorm,几乎所有 LLM 训练/推理框架都有自己的 Triton 版本。

bug 是什么:公式本该是 `sqrt(mean(x^2) + eps)`,kernel 写成了 `sqrt(mean(x^2)) + eps`。

为什么 allclose 测不出来:常规测试用随机高斯分布生成输入,均方值基本不可能接近零,这种情况下 eps 加在里面还是加在外面,数值上的差异极小,完全在容差以内。这个 bug 只有输入本身接近全零(比如 padding 位置的 embedding、或者某些神经元被剪枝/dropout 后整行是零)才会让两种写法的结果差出天壤之别。

真正该怎么判断:读 eps 加的位置对不对,再专门构造一个全零或接近全零的输入行去测,而不是只用正常量级的随机输入。

## FP 组(实现本身没问题,但严格容差 + 单一参考实现会误判)

### FP1. "并列时的合法 tie-break 差异" 这个套路,在两个不同 kernel 上各来一次
跟 FN3 一样的处理方式:这本来是两个独立 case(MoE 路由、top-p 采样),拆开看是同一个机制——"选择的时候出现并列,没有唯一正确答案,不同的合理规则选出不同结果,导致后面的连续输出对不上"。合并成一条,MoE 当主例子,top-p 当延伸变体。

**主例子——量化 MoE 路由在打分并列时的合法 tie-break 差异**
kernel 是什么:量化 MoE 的路由——用 fp16/int8 算每个 expert 的打分,选 top-2,再把两个 expert 的输出加权求和,vLLM 里是真实存在的结构。

差异是什么:两份实现都严格按算法写对了,但在两个 expert 打分并列的边界上(fp16 精度下两个 logits 舍入成一样),用了不同但都说得过去的 tie-break 规则,选出来的第二个 expert 不一样。

为什么会被 allclose 误判:因为不同 expert 是独立训练出来的、权重完全不同,选错一个 expert 会让最后加权求和的连续输出相对误差轻松超过 10%,远超常规容差。如果拿实现 A 的输出当参考去 allclose 检查实现 B,会直接判 B 错,但 B 根本没做错任何事,论文本身也没规定并列时该选哪个。

**延伸例子——Top-P 采样并列时的合法 tie-break 差异**
kernel 是什么:vLLM 真实存在的 Triton top-p/top-k 采样 kernel(`VLLM_USE_TRITON_SAMPLER`)。

差异是什么:概率质量在 cutoff 附近打平时(模型输出比较平滑的尾部分布时很常见),两种实现用不同但都合法的排序规则,选出的候选集合不完全一样,但两个集合都满足"累积概率 >= p"这个约束。

为什么会被 allclose 误判:如果直接比较两份实现算出来的"哪些位置被选中"的 mask 张量,会发现大量位置的 0/1 状态不一样,数值上差异巨大,但两个选择本质上都是对的——这跟你之前举的"CMU 排名并列"的例子是一回事。

真正该怎么判断:两个案例都一样——比较两个选中集合/两个选择结果的重合度(overlap/recall),或者看接在后面的连续输出是否合理,而不是逐元素比数值对不对得上。

### FP2. RoPE 两种数学等价但数值完全不同的实现约定
kernel 是什么:RoPE(旋转位置编码),几乎所有 LLM 的必备组件,Triton 实现到处都是。

差异是什么:RoPE 有两种主流写法——GPT-NeoX 风格(把维度切成前后两半分别旋转)和 GPT-J 风格(相邻两个维度交替旋转)。这两种写法数学上是等价的(只是维度重排的方式不同),但对同一个输入,两种写法算出来的中间张量在元素级别上完全对不上号。这不是我编的,HuggingFace transformers 历史上就因为混用这两种约定转权重出过真实 bug。

为什么会被 allclose 误判:如果拿其中一种写法的输出当参考,去 allclose 检查另一种写法,会发现几乎每个元素都不一样,误差大到离谱,但两种写法接到下游模型里效果是完全一致的。

真正该怎么判断:确认两份实现用的是不是同一种约定,如果不是,应该比较接到下游 attention 之后的最终效果,而不是直接比 RoPE 这一步的中间输出。

### FP3. "浮点求和顺序不同" 这个套路,在两个不同 kernel 上各来一次
跟 FP1 一样的处理方式:这本来是两个独立 case(cross-entropy、Mamba2 chunked scan),拆开看是同一个机制——"数学上完全等价,纯粹因为加法/求和顺序不同,规模越大差异越明显"。合并成一条,cross-entropy 当主例子,Mamba2 当延伸变体。

**主例子——Cross-entropy 单遍在线算法 vs 两遍算法的浮点非结合性**
kernel 是什么:Liger-Kernel 那种融合 CrossEntropy,词表动辄十几万,训练框架里很常用。

差异是什么:一种实现用在线(单遍扫描边算边更新最大值)算法,另一种用传统两遍扫描,两者数学上完全等价,只是加法顺序不同。

为什么会被 allclose 误判:词表很大(十几万)、精度是 fp16 的情况下,纯粹因为浮点加法不满足结合律,两种算法在单个 token 上算出来的 loss 会有百分之几的差异,虽然整个 batch 平均下来几乎看不出差别。如果拿严格容差去逐 token 比较,会被判成不一致。

**延伸例子——Mamba2 分块并行扫描 vs 串行递归的浮点误差累积**
kernel 是什么:Mamba2/SSD 的 chunked scan,state-spaces/mamba 官方仓库的 Triton 实现,现在线性 attention/状态空间模型很热。

差异是什么:分块并行扫描算法和最朴素的串行递归参考实现,数学上都是精确算法(不是谁近似谁),只是浮点求和的顺序完全不同——并行版本是树状归约,串行版本是一步步累加。

为什么会被 allclose 误判:序列越长,两种求和顺序累积的浮点误差差异就越明显,长序列下逐元素比较可能超出一个给短序列校准的容差,被判成"实现有问题",但其实这就是浮点运算顺序不同的正常表现,官方博客里也提到过这个现象。

真正该怎么判断:两个案例都一样——确认差异来源是不是纯粹的浮点求和顺序不同(而不是算法本身错了),看聚合后的整体结果/随规模增长的误差模式是否符合典型的浮点漂移特征,而不是较真单点的精确数值。

### FP4. FP8/FP4 量化 attention 天然误差比 fp32 大
kernel 是什么:Attn-QAT 这种 4bit attention,2026 年的论文,已经有 Triton 训练+推理 kernel。

差异是什么:低比特量化本身就意味着更大的量化噪声,这是设计上就该有的,不是 bug。

为什么会被 allclose 误判:如果验证系统用的是给 fp32/fp16 kernel 校准的那套固定容差,去卡一个正确实现的 FP4 kernel,会发现误差远超容差,直接判错。但这个误差是量化精度带来的正常噪声,不是逻辑错误。

真正该怎么判断:得知道这个比特宽度下"合理的误差范围"应该是多少(得去看量化方案本身、看论文里报的误差量级),而不是套用一个跟精度无关的固定阈值。

### FP5. 低精度训练里的 stochastic rounding(新补的机制)
kernel 是什么:低精度(bf16/fp8)训练里的梯度累积/权重更新 kernel。有些框架为了避免"总往一个方向舍入"带来的系统性偏差,故意在把 fp32 中间结果转回低精度存储的时候,用 stochastic rounding(按误差大小加权随机决定往上舍还是往下舍),而不是就近舍入。

差异是什么:同一份正确的代码,跑两次(甚至同一个 batch 输入跑两次),因为舍入用的随机数不一样,权重更新的具体数值每次都不完全一样——这是设计上就该有的行为,不是 bug。

为什么会被 allclose 误判:如果拿某一次 run 的输出当"标准答案"去 allclose 检查另一次 run(哪怕是同一份代码跑两遍),会发现每个元素都对不上,看起来像是完全不可控的错误,但这压根不是 bug,是这类 kernel 被设计成本来就该有的随机性。

真正该怎么判断:先确认这个 kernel 是不是本来就该用 stochastic rounding(看设计文档),如果是,应该看多次 run 的统计分布(均值、方差)是否符合预期,而不是逐元素比较单次输出。

### FP6. 真值接近零时,相对误差这个指标本身会失真(新补的机制)
kernel 是什么:任何涉及"输出可能接近零"的连续计算 kernel,比如 attention 里被大量 mask 掉之后剩下权重很小的位置,或者梯度计算里接近收敛、梯度本身很小的位置。

差异是什么:两份实现都是对的,某个具体位置的真实值极小(比如 1e-8 量级),一个实现算出 1.0e-8,另一个由于正常的浮点舍入算出 1.3e-8,绝对误差小到完全可以忽略。

为什么会被 allclose 误判:相对误差的定义是 |a-b| 除以 |真实值|,当真实值本身趋近于零,哪怕绝对误差小到可以忽略,这个比值也会被一个极小的数一除,直接爆炸到几十倍、上百倍。如果只用严格的相对误差容差去卡,这种位置会被判定成"完全不对",但其实是指标本身在这个区域失真了,不是 kernel 错了——这也是为什么真实的 `torch.allclose` 同时有 `atol` 和 `rtol` 两个参数,单用 `rtol` 就会栽在这种地方。

真正该怎么判断:对真值接近零的位置,应该看绝对误差而不是死磕相对误差(或者确认 `atol` 设得是否合理),而不是拿一个纯相对误差的容差去卡所有位置。

## 小结

12 个案例,6 个 FN(bug 真实存在但常规测试测不出来)+ 6 个 FP(实现本身没问题但严格容差 + 单一参考实现会误判),覆盖了 sparse attention(NSA)、投机解码、GPTQ int4、GQA、INT8量化、KV cache 量化、RMSNorm、MoE 路由、RoPE、cross-entropy、FP8/FP4 attention、Mamba2、top-p 采样这些真实 kernel 家族。

FN 这一组,拆到底其实是三种不同的"骗过测试"的机制,不是六种互不相关的技巧:

1. **测试场景覆盖不够广**(FN3、FN5):测试用的配置/形状/序列长度永远是"正常"的那种,bug 藏在没人测过的边界配置或者长时间累积的场景里。这类机制可以在几乎任何 kernel 上复制——只要找到一个"大家默认不会去测"的配置维度就行。
2. **随机测试数据踩不中特殊数值**(FN1、FN6):随机生成的测试输入,天然不会恰好撞上"两个值刚好相等"或者"数值刚好接近零"这种边界点,bug 只有在这些特殊点上才会发作。
3. **需要统计层面的证据,单次数值比较看不出来**(FN2、FN4):bug 造成的是分布层面的偏差,或者需要跟真实数据分布比才会暴露,单次、随机初始化的数值比较天然覆盖不到。

FP 这一组理了一遍,也是四种机制,不是六种:

1. **并列/tie-break 的合法歧义**(FP1):选择的时候出现并列,没有唯一正确答案,不同的合理规则选出不同结果。MoE 路由、top-p 采样是这个机制的两个变体。
2. **浮点求和顺序不同**(FP3):数学上完全等价,纯粹因为加法顺序不同产生误差,规模越大越明显。cross-entropy、Mamba2 是这个机制的两个变体。
3. **精度等级本身决定了容差该多宽**(FP4):量化位数低,噪声底线本来就该比 fp32 宽,拿同一套容差去卡不同精度等级不合理。
4. **数值表示约定不同**(FP2):数学等价但参数化方式不同,逐元素对不上,但接下游效果一致。
5. **kernel 本身设计上就该有随机性**(FP5):不是误差,是设计如此,单次确定性比较这个框架前提就不成立。
6. **比较指标本身在极端值区域失真**(FP6):不是 kernel 的问题,是"用什么指标"这件事本身选错了。

FN 三种 + FP 六种(其中两种各有两个变体),这个分类后面滚到 100 个应该会很有用——不是每个 kernel 家族硬凑一个 bug,而是每种机制在不同 kernel 家族上各复制几次,同时保证机制本身足够多样,不是同一个套路反复用不同的名字包装。
