# Solo 与 debate 的下一阶段实验设计（讨论稿）

2026-09-24。此文只提出待验证的假设；没有新增案例、修改运行时或启动付费实验。
保留 case_36–case_61、既有协议和所有结果。新任务应另建数据集，不改旧案例的输入范围。

## 为什么当前任务已经饱和

case_50–case_61 的 low/32768 三组结果是：无工具 13/36 正确、19 次明确误判、4 次弃答；
solo 与 debate 各 24/24 正确。两组工具臂的累计 API 估算分别为 $0.395888 和
$1.413265，相差约 3.57 倍，尚未匹配总资源。见 [OZ_REPORT.md](OZ_REPORT.md)。

多数合同直接给出唯一输入、参考公式、参考精度与判定阈值。例如
[Z 合同](eval_cases/case_61/problem.txt)和
[case_61 solo 主 probe](../traces_glm/case_61/solo/r2/probes/t7_probe.py)：
一次正确的独立参考计算和 GPU 对比已足够判定。继续提高算术难度，不一定提高
验证过程的难度。两组已有的正确主证据之外，debate 也出现了辅助诊断归因过强、
测量对象与字段名不一致等问题，见 [case_58–case_61 证据审查](OZ_TRACE_AUDIT_WXYZ.md)。

下一阶段假设：独立复核可能帮助发现错误实验、区分竞争解释、补足合同覆盖。
这是待测的流程优势，不能预先假定 solo 做不到，或假定多角色必然更准确。

## 首选：让验证器审查一个可疑但可复现的实验

除公开 kernel、明确合同、可执行输入生成器外，提供一份初始 probe 及其真实运行
输出。它只是待审查的实验材料，不是权威参考。所有臂得到完全相同的材料，并同样
被告知初始实验可能正确或错误；不能只提醒 Skeptic 审查它。输出不得伪造。

| 方向 | 可构造的具体机制 | 需要完成的验证动作 |
|---|---|---|
| 参考实现不独立 | 测试程序与 kernel 共用不稳定 FP32 计算；或候选修改输入后，参考才读取被修改的值 | 查清参考的数据来源、计算精度和计算时机；保存原始输入，用独立方式重算 |
| 覆盖范围不充分 | 状态缓存单步调用均通过，只有 append → 重排 → 再 append 的合法序列暴露状态关联错误；初始 tester 每步重置状态 | 从合同列出合法序列，维持真实状态执行，构造能区分两个解释的后续调用 |
| 指标与合同不一致 | 病态求解的残差很小但解误差大；或 tester 比较内部表示，而合同要求解码后的连续输出 | 确认合同真正要求的量，审查分母、聚合方式与表示转换，再取得决定性证据 |

这些都是合成的基准变体，不是在断言任何上游项目存在相应缺陷。现阶段优先研究
参考独立性和状态覆盖；指标不一致可能被 solo 直接读出，保留它作为可失败的假设。
所有方向仍以合同要求的连续输出或状态对应的连续输出判定，不凭内部索引差异定罪。

初步开发集为 3 类 × 4 例 = 12 例。每类都交叉覆盖以下四格，不能让“质疑初始实验”
本身成为猜标签的捷径：

| 内核真实状态 | 初始实验结论 | 期望验证器行为 |
|---|---|---|
| 合格 | 通过 | 保留正确结论，并核实依据 |
| 合格 | 不通过 | 找出实验问题，纠正误拒 |
| 不合格 | 通过 | 找出实验盲区，提供反例 |
| 不合格 | 不通过 | 保留正确结论，并核实依据 |

四格要求独立 oracle 确认，而非只依据构造者的代码意图。正确对照应具有相似长度、
接口和可疑特征，不能由文件名、明显注释或复杂度透露标签。若通过统一的穷举脚本
即可轻易解决某一类，也要接受该类可能继续打平的结果。

## 范围与 ground truth

固定输入的 case_36–case_61 不能用新输入反例推翻。涉及状态或多个子域的新任务，必须事先公开
有限输入族、合法操作、长度上限、重置语义以及所有需要满足的约束；初始 tester
只提供部分观察，不能用其样本集暗中缩小 problem.txt 明确声明的范围。

私有 oracle 对整个声明的有限域计算标签；正确例需要完整覆盖，错误例保存可重放
见证。用两个独立参考检查真实存储输入，运行真实 GPU 后冻结源码、输入、输出和
合同哈希。避免以不可控竞态、隐藏 seed 或无限输入域作为本轮的标签来源。

## 比较哪些系统

保留无工具、solo、debate 三组。区分 solo 与 debate 的主分析额外需要一个强对照：
solo-review，即同一个 agent 明确先验证、再审查自己的参考、输入覆盖和证据充分性。
它使用与 debate 相同的审查要求，且复核花费从同一总预算中扣除。

先评估当前 debate，再把改动版本命名为 debate-review，不能混用版本结果。建议的
改动是：初审先分别记录可证伪假设，再共享意见；Experimenter 提交 probe 代码和
原始结果；Skeptic 审查决定性证据并提出一个有区分力的反证实验；Judge 依据完成
的证据判断。假设和审查均应对应合同，不要求无理由反对，不以意见一致作为正确性。

为独立初审暂时延迟共享的是其他角色的观点，不是独占事实或工具。最终原始材料
与工具权限对 solo 同样开放。若 debate-review 有优势，再加入“独立 solo 多次运行
后汇总”的同预算对照，以检验交互是否比多次采样本身更有效。

## 预算必须按真实资源计算

目前 max_tokens 是每次模型调用上限；solo 的 10 rounds 与 debate 的 4 rounds 不
代表等预算。现有 tool_budget 计数包含 ledger 等操作，也不能直接表示 GPU 实验数。
正式新实验前，应在所有调用共同经过的入口记录和限制总模型资源，并在执行入口
记录实际计算资源，而非只限制最外层 rounds。

- 采用相同模型、推理设置和总 API 费用上限，记录输入、输出和推理 token；按几个
  预先固定预算点比较准确率和成本，不只报一个每调用上限。
- 给两种工具系统相同的累计 GPU 时间/执行资源上限；记录实际被执行的样本与步骤。
  一次 probe 可以循环很多输入，不能仅按 probe 次数视为同等实验量。
- 工具报错及模型调用错误也占用实际已花费资源。所有臂都预留最终总结机会；预算
  用尽、弃答、传输失败与明确错误分开统计。
- 相同合同、原始资料和检索能力。检查当前按角色进行的 prompt 压缩是否造成证据
  可见性差异，不能将 Judge 独享完整材料误解释为多角色推理优势。

## 如何归因与验收

先在开发集确认任务不是被一次通用 probe 全部解决。调试结束冻结构造规则，再
用未见的新 seed、布局和状态序列形成独立测试集；不能只保留 debate 赢过的案例。
每个配置至少做预先固定的重复，保留所有失败及弃答。小规模 pilot 只筛选方向，
不宣称统计显著或普遍优势。

主要报告最终正确率、明确误判、弃答和成本；辅助报告可重放证据是否支持结论。
对两组采用同一证据规则，不能要求 solo 给出额外证明。

要支持“复核有帮助”，trace 应展示：原来的错误或不足依据 → 审查发现具体缺口 →
新的区分性实验 → 有证据支持的纠正。只有讨论长度增加或多列几个风险不计为收益。
同时记录审查把原本正确结论改错的次数。

另做可控的诊断实验：固定同一份初始 probe、真实输出和暂定结论，分别交给 solo
自审与独立 reviewer 延续，比较修正错误和保留正确结论的能力。该诊断专门测审证，
不能替代从源码开始的端到端验证；端到端结果还须在不提供初始 tester 的条件下复验。

若 debate 仅优于默认 solo，而与 solo-review 打平，应把收益归因于复核流程。
若仅在更多预算下获胜，应报告成本与准确率权衡。若强 solo 在同预算下继续打平，
应保留这个结论，不再靠无关的源码长度或数值难度强行制造差距。
